# docs/decisions.md — decisions and boundaries

Read this for any design question, and before adding a dependency, a tool, a source format or a
setting. Section 2 holds decisions the user made; section 3 holds agent proposals the user has not
confirmed. Architecture and stages are in `docs/plan.md`.

## 1. What no change may add without a user decision

- Answer generation, a chat model client or any agent loop (D1).
- An HTTP API for non-MCP clients (D2).
- A profile or preset variable that sets several settings at once (D5).
- Authentication or per-caller access rights inside the server (D8).
- A second storage engine next to Lucene: a vector database, SQLite, a cache server (D6).
- An embedded script interpreter for custom chunking (D10).
- A step between a source and the index that is not one of the five of D15, or a format wired
  into the indexer instead of registered as a step implementation (D15).
- Loading step implementations from jars outside the server (D16).
- A converter program bundled with or required by the server (D17).
- Expressions, functions or conditions in `map` templates beyond `{value}` and `{a|b}` (D14): what
  templates cannot express is the job of a `command` source.
- A reranking model enabled by default (D12).
- An own interface or mechanism where Spring AI has an abstraction that fits (D28): use that one,
  or record in D28 why it does not fit.
- Spring AI's `VectorStore` as the storage of a collection, `TransformersEmbeddingModel`,
  `MarkdownDocumentReader`, `TokenTextSplitter` or a transformer that calls a chat model (D28).
- A dependency `docs/plan.md` does not name.

## 2. User decisions

| Date | Decision | Reason |
|---|---|---|
| 2026-11-14 | **D1. The server retrieves; it does not answer.** An assistant that talks to users is a separate service that uses this server and other MCP servers (for example `jdbc-mcp-server` for database reads). How that assistant connects to MCP servers is open | One search server serves several clients: assistants, coding agents, people |
| 2026-11-14 | **D2. No HTTP API for legacy (Java 1.7) clients in the first stage.** Add it later if a client needs it | Such clients talk to the assistant, not to this server |
| 2026-11-14 | **D3. The project is public** | Same as the sibling MCP servers |
| 2026-11-14 | **D4. Package root `ru.it_spectrum.ai.rag.mcp`**, modeled on `jdbc-mcp-server` | Consistency with the sibling servers; may change later |
| 2026-11-14 | **D5. One server for every environment; behavior is set by separate environment variables**: tool groups (`RAG_MCP_TOOLS_<GROUP>`, as `JDBC_MCP_TOOLS_*`), response limits. No profile variable for now. Allowed collections were dropped by D49 | A strong large-context model and a weak small-context model need different tool lists and limits; which data is served is independent of which model reads it, so a preset would forbid valid combinations |
| 2026-11-14 | **D6. A collection is an indexed connection to data**, configured like a connection in the sibling servers: one `collections.json` in the data directory, names of the form `<part>@<project>`, and inside each collection its sources, selection conditions, vector switch and model. One Lucene index per collection | The model the user already knows from `connections.json`; every developer can describe their own set of indexed directories; other projects become collections without code changes |
| 2026-11-14 | **D7. Indexes are built on our side and delivered ready.** A collection directory is self-describing and is served without the sources and without `collections.json` | The target site has no source repositories |
| 2026-11-14 | **D8. Audiences are separated by running several instances**, one data directory each (revised by D49: no list of allowed collections over a shared directory). No access rights inside one instance | A full collection set must be available for troubleshooting on a site whose assistant gets only a narrow set; hard isolation without an authentication subsystem |
| 2026-11-14 | **D9. Source directories are indexed directly.** The pipeline is D15. Built-in formats: `markdown` (front matter becomes fields), `tsv`, `yaml`, `jsonl`, `sql` (D21); `docbook` is deferred (D17). Format and chunking parameters are written per source in `collections.json` | Prepared knowledge already has structure (headings, front matter); a pre-export step per project is not required |
| 2026-11-15 | **D10. Custom reading is an external command, and a command is a step, not a format.** It produces text that the source's `format` then parses: run once it is the origin of a source (for example JSONL records of an export), run per file it is a `convert` step (for example to Markdown). It runs only while building an index | Any language; no interpreter inside the server; nothing extra to install where a ready index is served. As a format it could not convert each file and hand the result to a built-in reader |
| 2026-11-14 | **D11. Embeddings are computed in-process by default** (ONNX Runtime, a multilingual E5 model). A remote embedding endpoint is a second implementation of the same interface | Environments may have no embedding endpoint at all; indexed text then never leaves the machine; indexes for every environment are built with the same model |
| 2026-11-14 | **D12. Hybrid search fuses BM25 and vector results with reciprocal rank fusion (RRF).** A reranking model is added only if measurements on a question set show it is needed | RRF needs no model and no score calibration; a reranker costs CPU on every query |
| 2026-11-14 | **D13. A `rag-search` command searches from the command line without a model** (a chat model). It runs in a Spring context since D42 | On a site with a slow model an engineer still needs fast lookups |
| 2026-11-14 | **D14. Every source says how to cut and how to lay out**: a `split` block (where units end) and a `map` block (templates that turn the values of a unit into the id, title, breadcrumb, text and filter fields of the standard record). The same two blocks serve every format; without them a format's defaults apply | The first Markdown reader fixed one layout in code: the key only from `id`, fields only from front matter, cuts only by level. The mechanism must fit other projects' files without code changes |
| 2026-11-15 | **D15. A source is built by a fixed pipeline of five steps: origin → `convert` → `format` → `split` → `map`.** The origin lists items (files, or one run of a command); `convert` is a chain of text-to-text steps, empty by default; `format` parses text into a section tree or into rows; `split` cuts a tree into units; `map` lays a unit out as a record. Each step is an interface in its own package, and its implementations are found by name through one registry. A new format or converter is a new implementation, never a change of the pipeline or of the indexer | The plan for stage 2 was a closed list of formats, each wired into the indexer, with `command` as one of them. The same extract–transform–load shape with a fixed contract between steps lets steps be combined (convert to Markdown, then read Markdown) and added without touching the others |
| 2026-11-15 | **D16. Step implementations from external jars are provided for, not implemented.** The registry and the step interfaces are designed so that a jar can add an implementation later; no loader is written until it is needed | Not needed now; the architecture must not rule it out |
| 2026-11-15 | **D17. Pandoc is a documented example of a `convert` command, not a part of the server.** A DocBook reader is not written now: the manuals are converted to Markdown inside their own project and indexed as Markdown. The reader may come later, as a reference implementation of a tree format | One program turns many formats into Markdown, which the server already reads; `mail-mcp-server` is built this way. The server stays without a required external program |
| 2026-11-15 | **D18. Named readers.** A top-level `readers` object in `collections.json` holds reusable sets of `convert`, `format`, `split` and `map`; a source names one with `reader` and may override single keys | The same way of reading is written once and used by several sources and collections, as `models` is for vectors |
| 2026-11-15 | **D19. Step implementations are Spring beans, and the registry is a bean that receives them as lists.** `rag-index` starts the application context with the MCP server switched off instead of running before Spring; `rag-search` keeps running without a context (D13; since D42 every command starts the context). The registry has a plain constructor, so unit tests build it without a context | Building is rare and takes longer than a context start; one wiring mechanism for the whole project; a step can take properties and other beans (the embedding model, the command runner); a jar of D16 adds its steps as beans |
| 2026-11-15 | **D20. Examples and test data are anonymous in content and real in shape.** The synthetic knowledge under `testdata/` and the examples in the documents reproduce the formats, directory layout, front matter keys and file shapes of the first real corpus the server is built for, with invented text and names. That corpus holds Markdown with YAML front matter, YAML data descriptions, TSV catalogs, SQL files and a JSONL question set; its DocBook manuals live in separate directories. Where the corpus is stays outside the repository (`.local/`) | The first collections are built from that corpus, so a format or layout it has must work on the first real build; the repository is public (D3), so nothing of the corpus itself may be copied |
| 2026-11-15 | **D23. The `lookup` group finds records by a value without its field name.** One tool, `lookup(collections, value)`, returns the records of which a key field has the value, compared whole and ignoring case. The key fields are listed per source in `map.keys` and recorded in the manifest; a source without `map.keys` takes no part in lookups | An exact match on a known field is already `search` with `filters`; what a model lacks is the name of the field a code, a class name or a message text is in |
| 2026-11-15 | **D22. A YAML file is one record unless the source names a list.** Without `split.list` the whole file is one unit: its top-level scalars and lists of scalars are values, the file text is `{body}`. With `split.list` every item of that top-level list is a unit, and the scalars of the file stay available. The format receives the `split` block of its source for this | The first corpus has three YAML shapes: a list of entries under one key, a description with a list of values, and one table per file whose columns are a mapping. "An item of a named list" covers only the first two; a whole file covers the third without a selection language |
| 2026-11-15 | **D24. Embeddings run on ONNX Runtime with DJL's Hugging Face tokenizer.** `com.microsoft.onnxruntime:onnxruntime` runs the model, `ai.djl.huggingface:tokenizers` reads its `tokenizer.json`; the vector is the masked mean of the token states, scaled to unit length. Before the tokenizer is first used the server sets `OPT_OUT_TRACKING` and DJL offline mode and points DJL's native cache to `<data-dir>/cache/djl`. ONNX Runtime is pinned to 1.20.0: 1.21 and later need `msvcp140.dll` 14.40+, and the JDKs in use ship 14.31–14.36 in `bin/`, which Windows loads first (1.32 crashed the JVM, 1.21 failed to load) | ONNX Runtime has no tokenizer, and DJL's is the reference implementation in Rust; without the two settings DJL probes a cloud metadata address on every tokenizer creation and writes under the home directory (invariant 5). The pin keeps the server working on Windows out of the box |
| 2026-11-15 | **D25. The default model is `intfloat/multilingual-e5-small` (FP32 ONNX, 384 dimensions).** The operator downloads `model.onnx` and `tokenizer.json` from the `onnx/` folder of the model on Hugging Face; the server never downloads anything. Unit tests use a deterministic stand-in; the real model is checked by a test that runs when `RAG_MCP_TEST_MODEL_DIR` is set and by building a collection from the first corpus | Three times faster to embed than `-base` with a close Russian retrieval score (RT-07 of `mail-mcp-server`); model files cannot be in the public repository |
| 2026-11-15 | **D26. Vector settings and search modes.** (A model type that names a Spring AI bean is added by D43.) `collections.json` gets a top-level `models` object (`type`, `queryPrefix`, `passagePrefix`, `maxTokens`) and per collection `vectors: {"model": "<name>"}`. The files of a model are always in `<data-dir>/models/<name>/`, on the building and the serving side; there is no path setting. The manifest keeps the model name, its parameters, the vector size and the SHA-256 of its files; a difference is an error for vector and hybrid search. `search` takes `mode`: `lexical`, `vector` or `hybrid`; without it, hybrid for collections with vectors and lexical for the others. `rag-search` takes `--mode`. Fusion is Lucene's `TopDocs.rrf` with k = 60 | One place for model files makes delivery a copy of `models/` next to the collections (D7); the hash check catches a collection served with another model |
| 2026-11-15 | **D27. Vectors are cached by a hash of the model and the text** (formerly P4), in a Lucene index under `<data-dir>/cache/embeddings/`, so the cache is not a second storage engine | Rebuilds and collections sharing a model do not recompute unchanged records |
| 2026-11-15 | **D28. Spring AI is the base wherever it has an abstraction that fits.** The server uses Spring AI's interfaces and implementations for the MCP server, embedding models (D29), filter expressions (D30), the document type at its boundaries (D31) and document readers (D32). Own code stays only where Spring AI has nothing or contradicts a decision, and each such case is listed here with its reason: (a) storage and search are Lucene, not a `VectorStore`: `SearchRequest` has no lexical or hybrid search, there is no Lucene store, and `add`/`delete` do not fit an index that is built by `rag-index` and delivered ready (D6, D7); (b) fusion is Lucene's `TopDocs.rrf`: Spring AI has only `ConcatenationDocumentJoiner`; (c) the ONNX model is the server's own `EmbeddingModel` and not `TransformersEmbeddingModel`, which downloads a default model from the network, does not scale vectors to unit length, does not say which inputs were cut, brings DJL's PyTorch engine and model zoo and leaves the ONNX Runtime version to the BOM against the pin of D24; (d) the Markdown reader and the splitter are own (D59); (e) the five steps of D15 stay: Spring AI's reader–transformer–writer chain has no place for `split` and `map` settings per source; (f) `KeywordMetadataEnricher` and `SummaryMetadataEnricher` need a chat model (D1). Checked against the 2.1.0-RC1 source | The project had drifted to own solutions while only the MCP server came from Spring AI. Standard interfaces let ready implementations be plugged in (remote embedding models, readers of PDF and Office files), give users a filter language models already know, and keep the server usable from other Spring AI code |
| 2026-11-15 | **D29. An embedding model is a Spring AI `EmbeddingModel`.** The indexer and search embed through that interface; a model type of `models` (a `ModelType` bean since D43) returns an `EmbeddingModel` and what identifies its vectors (type, vector size, file hashes). The in-process ONNX model is the server's own implementation (D24, D28 c); a remote endpoint (D11) is a Spring AI implementation registered as another type. What the interface does not give stays in the server's wrapper: the identity for the manifest and the cache, the prefixes, and which inputs were cut, which a model of this server reports under the response metadata key `truncated`. Implemented | A remote model then needs a loader, not an implementation; the interface is plain Java, so `rag-search` keeps running without a Spring context (D13) |
| 2026-11-15 | **D30. Search filters use Spring AI's filter expressions.** A filter is a `Filter.Expression`, written in the text syntax of `FilterExpressionTextParser` (`subsystem == 'billing' && kind in ['faq', 'howto']`) and converted to a Lucene query by the server. Adds the dependency `spring-ai-vector-store`. The map of field to value stays next to it: `search` takes `filters` and `filterExpression`, `rag-search` takes `--filter` and `--filter-expression`, and with both the expression must hold together with the map, which is its equality conditions joined by "and". Implemented | Filters were equality joined by "and"; the expression language adds "or", "not" and lists in a syntax that is documented and that models know. The map stays because the simple case stays simple for a weak model and existing calls keep working |
| 2026-11-15 | **D31. Spring AI's `Document` is the record type at the boundaries, not inside.** The result of a source pipeline is offered as a `DocumentReader` and the indexer accepts records as a `DocumentWriter`; one mapping turns the server's record into a `Document` (id, text, the other values as metadata) and back. The steps of D15 keep their own shapes. Fields are metadata entries under their own names, each a list of strings; the other parts of the record are metadata under names starting with `rag.`, which a field may not use. Implemented in the package `document/`; the classes of `ingest/` name no Spring AI type | The pipeline is finer than Spring AI's chain and is not replaced; the standard type at its ends lets Spring AI readers feed the index (D32) and other Spring AI code consume the records |
| 2026-11-15 | **D32. Spring AI document readers become formats.** `spring-ai-tika-document-reader`, `spring-ai-pdf-document-reader` and `spring-ai-jsoup-document-reader` are wrapped as `format` step implementations registered by name (D15); each dependency is added together with its format, when a corpus needs it. They read on the building side only. The first is the PDF reader, chosen by the user on 2026-11-15 before a corpus needs it: the format `pdf`, one record per page (`docs/collections.md`). Tika and Jsoup are not added | PDF, Office and HTML sources without an external converter (D17 stays the way to get structured Markdown); the text of such a reader comes without the heading tree |
| 2026-11-15 | **D33. Semantics of filter expressions.** In a filter expression, `!=`, `nin` and `NOT` hold for a record without the field, as `not` of `where` does; a number or a boolean is compared as its text; `<`, `<=`, `>`, `>=` compare text and accept only quoted values. Implemented (`docs/search.md`) | Field values are indexed as lower-cased text terms with no type; numeric ranges would need typed fields, a change of the index schema |
| 2026-11-15 | **D34. A format may read the file of an item itself (`Format.readsFile`, `parseFile`), as a binary format must.** Such a format takes no `convert` steps and no `command` origin, which the source check reports. Implemented for `pdf` | The pipeline of D15 gave a format only text; the alternative, bytes in `SourceText`, would change the shape every other step takes |
| 2026-11-15 | **D35. The `pdf` format keeps pages, not sections.** Spring AI's `ParagraphPdfDocumentReader` cuts by the outline, but fails on a file without one, and the first corpus has no PDF to measure against. Implemented | A page always exists; sections by outline can come as a setting when a real PDF corpus shows the need |
| 2026-11-15 | **D36. Requirements of the specifications are not indexed.** They live outside the knowledge directory of the first corpus; the `spec:` references of its question set stay unreachable and `rag-eval` reports them apart | The server indexes prepared knowledge; the specifications are a source for writing it, not part of it |
| 2026-11-15 | **D37. Rows of Markdown tables can be records** (`split.tableRows`): every row of a table in a unit of a Markdown source becomes a unit, with its cells as `{column.<n>}` by position (and `{column.<name>}` when the header is a name), `{row}` and a one-row table as `{body}`; the rest of the unit is left out. Implemented; the manifest records the setting (schema 8) | The symptoms of the first corpus are rows of a table in one Markdown file, and its question set names them by number; a section of 35 rows as one record cannot be found by a symptom. Positions, because the real headers are Russian phrases |
| 2026-11-15 | **D38. Search returns the best section of each document** (formerly P24). A page holds at most `perDocument` records of one document, 1 by default; `search` takes `perDocument`, `rag-search` and `rag-eval` take `--per-document`. Only sections are limited: the records of a Markdown source cut by headings share a group, the document key; a row of a catalog, a table or a row format is a group of its own. The group is stored in the index (schema 9). `total` still counts matching records. Implemented | On the first corpus sections of one document filled the top: hybrid found 15 of 17 questions within 10, and 17 of 17 with the limit, MRR 0.66 → 0.69, recall@10 0.72 → 0.76. Catalog rows must not be limited: they are separate answers in one file |
| 2026-11-15 | **D39. `split.maxChars` keeps its default 2500** (formerly P22). Measured | On the first corpus 1000 and 1500 changed hybrid MRR by at most 0.01 and recall@10 by at most 0.06 in either direction, while making 45% more records at 1000 |
| 2026-11-15 | **D40. Limits for a model with a small context** (formerly P23): `RAG_MCP_SEARCH_DEFAULT_LIMIT=5`, `RAG_MCP_SEARCH_MAX_LIMIT=10`, `RAG_MCP_RESPONSE_MAX_CHARS=4000`; the defaults (10, 50, 20000) stay for strong models. A recommendation in `docs/search.md`, no new setting | 5 hits are about 2,000 characters of snippets and still hold the expected record for 14 of 17 questions; the size cap bounds a page of long snippets |
| 2026-11-15 | **D41. No reranker yet** (formerly P25): not until the question set has at least 50 measured questions and hybrid or lexical misses are shown to be ranking errors, not gaps of the collections (D12) | With 17 questions one question moves MRR by up to 0.06; a reranker costs CPU on every query |
| 2026-11-15 | **D42. Every command runs in a Spring context without the MCP transport** (revises D13 and the part of D19 that keeps `rag-search` out of Spring). `rag-search` and `rag-eval` start the application context as `rag-index` does, so a model or another step can be a bean configured by Spring AI. Implemented: `Cli.context` starts the context for all three commands. Measured on a desktop with the first corpus, JVM start included: a lexical `rag-search` went from 0.85 s to 1.8 s, a hybrid one from 2.8 s to 3.8 s; stdout carries only the report and stderr stays empty | Spring AI provides embedding models as auto-configured beans; a command without a context cannot use them, which kept remote models (D11) a hand-written factory. `rag-search` takes about 0.8 s for a lexical query today; the cost is what the context adds |
| 2026-11-15 | **D43. A model of `models` may be a Spring AI `EmbeddingModel` bean.** A model type names a bean configured by Spring AI properties (for example `spring.ai.openai.embedding.*`); the server keeps only what Spring AI does not give: the identity recorded in the manifest and the query and passage prefixes. Model types become beans, as steps are (D19), so a type is added without changing the registry. Needs D42. Implemented: the type `bean` takes the bean whose name is the key of the model under `models`, so the manifest, which records that name, still serves without `collections.json` (invariant 4); its identity in the manifest is the bean name and the model its first response names, and its vector size that of a probe embedded on load. No Spring AI provider starter is a dependency yet: one is added with the endpoint of a site (D11) | The remote endpoint of D11 becomes configuration of a ready Spring AI implementation instead of code; invariant 5 holds because such a model is still an explicit setting per model |
| 2026-11-15 | **D44. Records are embedded as Spring AI documents.** The indexer gives the model the `Document`s of D31 through `EmbeddingModel.embed(documents, options, batchingStrategy)`; what is embedded (the passage prefix, the breadcrumb, the text) is the document's content formatted for `MetadataMode.EMBED` by a `ContentFormatter`, and batches come from a `BatchingStrategy` of the server (Spring AI's `TokenCountBatchingStrategy` counts OpenAI tokens). The embedding cache (D27) stays. Implemented: `RecordContentFormatter` and `CountBatchingStrategy` (64 documents); the model is called through `EmbeddingRequest` per batch, because `EmbeddingModel.embed(documents, …)` embeds `getText()` and drops the response metadata that says which inputs were cut. The embedded text is unchanged: a rebuild of the first corpus took every vector from the cache | Removes the server's own text assembly and batching where Spring AI has the interfaces; the embedded text stays as D61 describes |
| 2026-11-15 | **D45. The streamable HTTP transport of stage 5 is the Spring AI MCP server starter's**, not an own one. Implemented ahead of stage 5: `spring-ai-starter-mcp-server-webmvc` (Tomcat and Spring MVC, 18 modules, the jar grows by about 12 MB); `RAG_MCP_TRANSPORT=http` serves `/mcp` on `RAG_MCP_HTTP_ADDRESS` (default `127.0.0.1`) and `RAG_MCP_HTTP_PORT` (default 8080), stdio stays the default; the stdio-only tool-execution customizer applies to stdio only | Spring AI provides it; D2 is not touched, since it is MCP over HTTP and not an API for other clients |
| 2026-11-15 | **D46. The in-process model reports Spring AI observations.** `OnnxEmbeddingModel` uses the observation conventions of Spring AI embedding models (for example through `AbstractEmbeddingModel`), so embedding time and batch sizes are measured as for any Spring AI model. Implemented: every call is an `EMBEDDING_MODEL_OPERATION` with Spring AI's default convention (`gen_ai.client.operation`, provider `onnx`, the model's name and vector size), reported to the context's `ObservationRegistry`; the server bundles no metrics backend, so nothing is recorded until one is configured | Metrics for free where Spring AI defines them; nothing to invent |
| 2026-11-15 | **D47. The transport is one setting, `RAG_MCP_TRANSPORT`** (formerly P26), from which `config/TransportSettings` derives the Spring settings it needs (`spring.main.web-application-type`, `spring.ai.mcp.server.stdio`, the protocol). Implemented | Setting the web application type and stdio apart would let a server start with both or neither transport |
| 2026-11-15 | **D48.
